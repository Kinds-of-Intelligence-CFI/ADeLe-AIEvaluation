# Action control and execution
#! ADeLe v2 (agentic) — DRAFT for team review | version: v2-draft | source: Paolo_Pablo | revised: 2026-07-27 | validated: labs/rubric-qa rounds 5-21 (incl. rivercross)

This rubric assesses the level of cognitive demands associated with action control and execution: carrying out a plan and keeping it on track — monitoring progress, deciding what to advance next and when a part is done, detecting deviations (a step done wrong, or a plan no longer working), and recovering at the right grain, from redoing a step to revising the plan. An action is the carrying-out of one plan step: the finest unit that could be separately instructed, done wrong, and redone (posting an entry, making a tool call, writing a section); words and tokens are not actions. Feedback is information from the environment that establishes, without further work, that an action or subtask has succeeded — not an observation from which success must still be worked out, nor an interlocutor's acknowledgement.

Distinguishing action control from neighbouring dimensions. Noticing that a plan needs revision is assessed here; devising the revision is Planning (PLp), as is the deliberation that finds or chooses a step. Execution length is Volume (VO), reasoning about other agents is Mind Modelling (MSm), hidden or changing environment state is Situational and Environmental Understanding (PLs), and holding interim results in mind is assessed by the memory dimensions (MMs, MMe) — a routine run off by rote, with no monitoring because none is needed, is Procedural Memory (MMp). Such features raise this demand only insofar as they make deviations harder to detect or recover from. How long the task runs, how many agents are involved, how much the environment changes and how open-ended the goal is are assessed as difficulty factors in their own right and do not raise this demand by themselves.

Level 0: None. The task requires no execution control: it is completed by a single atomic action — no monitoring, sequencing or recovery is involved, and the action succeeds or fails at once.
Examples:
* Say whether checkmate can be delivered in one move in a given chess position.
* Look up a single fact with one search-engine query.
* Select the figure that fits the pattern from A to E.
* Find the winning line in a given chess position and write it down. (All the difficulty is in finding the plan; carrying it out is a single act of transcription.)

Level 1: Very low. Tasks at this level require execution to be checked by the environment at every step: feedback arrives after essentially every action — each action's success or failure is signalled immediately — so an error is caught and corrected on the spot and no self-monitoring is needed.
Examples:
* Reset a password by following the prompts on a website.
* Navigate to an address following turn-by-turn directions, where any wrong turn is immediately flagged and rerouted.
* Cook from a recipe in which each step's outcome makes success immediately apparent before moving on.

Level 2: Low. Tasks at this level require execution to be checked at checkpoints: feedback arrives roughly once every two to ten actions at natural checkpoints such as the completion of a subtask, or at the end of a short task. Between checkpoints the agent must keep track of what has been done and verify its own steps, but an error discovered at a checkpoint is cheap to localise and redo.
Examples:
* Assemble a flat-pack wardrobe, where nothing reveals whether a stage was done right until a whole sub-assembly is stood up and either fits together or does not.
* Follow a tutorial to implement a small transformer network, running the code at each milestone.
* Complete a long structured application form that validates each section on submission.

Level 3: Intermediate. Tasks at this level require execution to be self-checked: stretches of tens of actions — or the whole task — pass without any feedback, so the agent must set its own criteria for being on track, monitor progress against them, and decide when each part is finished, which open subtask to advance next, and whether the current approach is still on course. A task remains at this level as long as an error, once noticed, can be fixed where it occurred without redoing the work that followed.
Examples:
* Write and polish the introduction of a scientific paper, judging for yourself when each paragraph is finished.
* Summarise a long document and extract its main arguments. (A weak paragraph is fixed in place; nothing downstream depends on it.)
* Draft the claims of a patent from the paper it is based on, with no examiner feedback until the whole set is filed.

Level 4: High. Tasks at this level require execution to be safeguarded against propagation: feedback is equally sparse, but an undetected error silently corrupts the work that follows, so monitoring must be proactive — the agent must anticipate where slips would matter, insert its own checks, and, when an error is found, trace its consequences and rework everything that depends on it — or recognise that the approach itself must change before more work is built on it.
Examples:
* Manually reconcile a year of a small business's ledger across twelve monthly statements, where a misposted entry in an early month silently unbalances every subsequent account until the final totals are compared. The reconciliation procedure is given step by step. (Contrast the summary at Level 3: there an error is fixed in place; here it forces rework of every month that followed.)
* Extend a large codebase that has no test suite, where a subtle early bug only surfaces much later in dependent components. What to build is specified in advance; the difficulty is carrying it through.
* Translate a long legal contract, where a mistranslated defined term early on corrupts every later clause that uses it. The glossary and translation brief are supplied.

Level 5: Very high. Tasks at this level require execution to be safeguarded before every commitment: some actions are irreversible, so errors cannot be corrected even when found — they must be prevented, and each consequential step verified before it is taken. A consequential irreversible step places a task here on its own, whether or not feedback is sparse and whether or not errors propagate: an action confirmed the instant it is taken is still unrecoverable if it cannot be undone. Time pressure raises the demand only by forcing commitments before they can be verified.
Examples:
* Migrate a live production database without a rollback mechanism, where a wrong step corrupts data irrecoverably.
* Carry out a multi-step synthesis of a scarce compound, where a failed step destroys the material. (Contrast Planning, which assesses devising the route: here the route is known and the demand is that no step can be retried.)
* Conduct an archaeological excavation, where each removal destroys context that can never be re-examined. The excavation grid and recording method are prescribed.
